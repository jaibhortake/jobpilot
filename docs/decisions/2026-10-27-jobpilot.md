# Decision: JobPilot — personal job discovery, CV tailoring and contact-finding assistant
Date: 2026-10-27

## Problem
Jai (single user, 2026 B.Tech EXTC graduate, currently GenAI Engineer) applies to software / data / AI roles across ~125 company career sites. Checking each site by hand, tailoring the LaTeX CV per job, and working out recruiter email addresses is slow. The tool must find the latest jobs on sites the user supplies, rank them against the user's profile, produce truthful tailored CVs and cover letters, propose recruiter email addresses with honest confidence, and track everything in one dashboard. The user applies and sends emails manually.

In scope: discovery from user-supplied career links, match scoring with thumbs up/down feedback, CV tailoring (reword + reorder only), cover letter, contact/email-address finder, application tracking.
Ruled out by the user: auto-submitting applications, form autofill, writing email body text, LinkedIn scraping, SMTP mailbox probing, cloud hosting, multiple users, scheduled discovery (manual refresh only), screening-answer drafts, company briefs.

- Functional: new flows (import, discover, score, tailor, cover, find-email, track). No existing flow changes.

## Contracts and constraints
- Authority: the master `.tex` is the only source of facts about the user. A career site is authoritative for its jobs. A user-entered verified email outranks any guess, always.
- Identity: job = (career_source_id, external job id), falling back to a hash of the canonical URL. Company = normalised domain. **Superseded by user ruling 2026-10-28:** company = case-insensitive trimmed name. The domain is a nullable attribute, filled only from verified contacts or a confirmed web search, never from a career-page URL (career hosts like `avature.net` and `metacareers.com` are not the company's mail domain). Contact email = case-insensitive unique (DB constraint plus UI duplicate warning). Person = (normalised full name, company).
- Currentness: jobs keep `first_seen_at`, `last_seen_at`, `posted_at` (nullable). A job missing from a successful crawl of its source is marked `closed`, not deleted. Sort key: `posted_at` falling back to `first_seen_at` (many feeds give only relative dates like "Posted 3 days ago", parsed when present).
- Lifecycle: job `new → shortlisted → materials_ready → applied → interview → offer | rejected`, plus `dismissed` and `closed`. The user moves states manually, backwards allowed; every change is logged.
- Consumers: the dashboard only. Generated PDFs are files under a data volume, referenced by DB rows.
- Environment: Windows 11, **native installs, no Docker** (user ruling 2026-10-27; Docker is not installed). Postgres 17 via winget `PostgreSQL.PostgreSQL.17`; LaTeX via MiKTeX (`MiKTeX.MiKTeX`, `pdflatex`), because Tectonic has no winget package. Runs only while the PC is on, single writer. Backend and frontend start with one script (`scripts/dev.ps1`), run with PowerShell 7 (`pwsh`, user-approved prerequisite 2026-10-28). LLM: see commitment 10. A check that hits the active provider's rate limit skips AI extraction and reports it as skipped.
- ATS feeds (probed 2026-10-27, tier 3): the Workday `POST /wday/cxs/{tenant}/{site}/jobs` returned 220 jobs for Rockwell with `postedOn` text and locations; the Oracle HCM `recruitingCEJobRequisitions` REST answered for JPMC; the SmartRecruiters `v1/companies/{id}/postings` returned 76 jobs with ISO `releasedDate`. Ashby, iCIMS and Eightfold are unprobed; the plan pins each with a recorded fixture before its reader is built.

Input facts measured (tier 3, read from the files on 2026-10-27):
- Sheet: ~125 rows, columns `Company | Website | Hr contacts`; HR contacts empty.
- ATS mix: Workday 38, Oracle Cloud 6, SmartRecruiters 2, iCIMS 2, Eightfold 2, Ashby 2, Avature 1, ~70 custom pages (many JavaScript-rendered: Google, Meta, Apple, Microsoft).
- CV: `resume.cls` custom class; content in `rSection` environments, experience as `\textbf{Title} \hfill dates \\ Org` + `itemize`; projects as `\textbf{Title} \\` + paragraph. Parseable structurally.

## Approaches considered
### A. Minimal: one Python app, Streamlit, SQLite, AI extraction on every page
Fast to build, but sends every page through the LLM (slow, quota-heavy, non-deterministic), has no backend/frontend split (contradicts the user's production-grade requirement), and is hard to test.
### B. Modular backend + React frontend, ATS readers first, AI fallback
Per-ATS readers call each platform's JSON feed with no AI. Unknown sites use Playwright + LLM extraction. LiteLLM routes calls per task to Claude or Groq. Tailoring is a LangGraph pipeline with a fact-trace check. Matches the reference stack, spends AI only where needed, and readers are testable against recorded fixtures. Cost: ~4–6 weeks; readers need health monitoring.
### C. Fully agentic browsing for every site
Least per-site code, but slow, costly, non-reproducible and hard to test. Rejected against "reliable".
### E. (ideal, then adjusted)
- Ideal design: B plus a background scheduler, and embeddings for matching.
- Adjustments:
  | # | Ideal wanted | Existing decision in the way | Concession | Cost |
  |---|---|---|---|---|
  | 1 | Scheduled crawls | User chose manual, on-demand checks | "Check company" per company the user names (no "Refresh all", ruling 2026-10-28) | No alerts while away; only companies the user asks about are searched |
  | 2 | Hosted embedding API | Free/local preference | Local Ollama `nomic-embed-text` | Slightly weaker semantic match; needs Ollama running |
- Resulting design: the ideal, adjusted, is Approach B.
- Distance from ideal: no scheduling.
- What would close the gap later: add an APScheduler job calling the same refresh service.

## Decision
Chosen approach: **B**.
Distance from the ideal: E's resulting design (no scheduler, local embeddings).
Why this won: about 45% of companies run on known ATS platforms (tier 3, measured from the sheet), so deterministic readers cover the biggest group cheaply. It is the only option meeting the separate-folders, production-grade requirement. Model switching comes free via LiteLLM (tier 2, used in the reference project).
What would reverse this decision: the phase-1 probe shows most ATS feeds are blocked or need login. Then the AI-browser fallback becomes primary and C's cost must be re-weighed.
Scenario table: not a rule change (greenfield).
Why the others were rejected: A fails the architecture requirement and the AI quota; C fails reliability and testability.
Delivery (user ruling 2026-10-27): built as three plans against this one document:
- Part 1: find and rank jobs (commitments 1–5).
- Part 2: materials (6–7).
- Part 3: contacts, finder and tracking (8–9).
Commitment 10 is carried by whichever part first needs a model.

### Design commitments
1. **Sources:** import from `company details.xlsx` (Company, Website, Hr contacts) and add/edit/delete single links in the UI. ATS type is auto-detected from the URL and can be overridden. Each source shows health (last success, jobs found, last error).
   - User ruling 2026-10-28: the sheet is a **company directory**, not a crawl list. Quote: "only refresh and check that particular website only which the users specifies no need for going for all from my sheet user will tell the link and company or just company name".
   - Input is "company name" (looked up in the directory) or "link + company".
   - A name not in the directory → the app web-searches for the careers page and shows candidate links; the user confirms one before it is saved and checked.
   - A single job-posting link can also be added directly ("add job by URL"), with a pasted job description as fallback.
2. **Discovery:** on-demand "Check company" for the one company the user names (re-checkable later). There is no "Refresh all" (superseded, ruling 2026-10-28). Readers: Workday, Oracle HCM, SmartRecruiters, Ashby, iCIMS, Eightfold, Greenhouse, Lever (the last two are cheap to add even if absent from the sheet). Where an ATS search supports it, pre-filter server-side by role keywords and location. Otherwise the generic reader renders with Playwright and extracts with the LLM; if the rate limit is hit, the remaining generic sources are skipped and reported.
3. **Profile and filters:** derived from the master CV, editable in the UI: role keywords (software, data, ML, AI, GenAI, security), locations (default India + remote), experience 0–2 years. Filters are UI controls.
4. **Ranking:** all open jobs, sorted by date (posted_at, else first_seen_at), with a match score (0–100) and reasons. Score = local embedding similarity between CV and JD plus keyword/skill overlap plus a learned adjustment from thumbs up/down (per-feature weights over title terms, company, skills). Hard filters remove non-matching roles. Thumbs-down offers "hide similar".
5. **CV selection:** the UI lists master CVs. `Jai_Bhortake_CV` (tex source) is tailorable; `jai_cv_hardware.pdf` is selectable as a static PDF only, until a `.tex` is added.
6. **Tailoring:** reword + reorder only. Pipeline: JD analysis → select and reorder sections and bullets → reword using JD vocabulary → **fact check**: every output bullet maps to a source bullet ID; every skill, tool, number, date, title and organisation in the output must appear in the master CV; failures are reverted to the original wording and listed → render via the same `resume.cls` → compile with `pdflatex` (MiKTeX) → ATS check (text extractable, keyword coverage report, one page). Output stored as a versioned `cv_version` with its trace map.
   - User rulings 2026-10-28:
     - A **standalone "Tailor CV" page** where the user pastes a job description (+ company, title) and gets the tailored PDF and an ATS score. The pasted job is saved as a manual job so it can be tracked.
     - **Goal: maximum ATS score while staying truthful:** after rewording, the tool lists the description's keywords missing from the CV; the user ticks the ones they genuinely have, and only those are added. Confirmed skills are remembered for future jobs and are added to the Skills section only (never written into experience bullets as claims of past work). This supersedes "reword + reorder only" for the Skills section; bullets remain reword + reorder only.
     - Each rewritten bullet can be accepted or reverted by the user before the final PDF.
     - The job's status is not changed automatically.
7. **Cover letter:** generated per job only from master-CV facts plus the JD and company facts from the job page. Same fact check. Editable in the UI, exported as PDF.
8. **Contacts and email finder:**
   - The contacts UI adds, edits and imports verified emails. Unique case-insensitively; a duplicate shows the existing record instead of creating one.
   - Web search sits behind a `SearchProvider` interface. The default is DuckDuckGo via the `ddgs` package (free, no key). Brave Search API is an optional provider, enabled by setting `BRAVE_API_KEY`. (SearXNG was dropped with Docker, user ruling 2026-10-27.)
   - Finder input: person name + company. Steps: resolve the company domain (sources table, else web search) → search public pages for the person's exact address or role confirmation → infer the domain's pattern from verified contacts at that domain plus addresses found on public pages → MX check on the domain.
   - Output: up to 3 ranked candidates, each labelled `verified` (user-entered), `found` (seen verbatim on a public page, with URL), `pattern` (matches a pattern seen at the domain, with count) or `guess` (common-pattern prior only). Each has a confidence and the evidence. A guess is never shown as verified. No SMTP probing.
9. **Tracking:** dashboard of jobs by state, CV/cover versions per job, contacts linked to companies/jobs, application dates, follow-up reminders (date field plus "due" list), responses.
10. **Models:** settings page plus config map each task (`extract`, `score_explain`, `tailor`, `fact_check`, `cover`) to a LiteLLM model id. Default Claude (Sonnet-class for tailor/cover, Haiku-class for extract), Groq Llama as the alternative. API keys live in `.env`, never in the DB.
    - User ruling 2026-10-27 (supersedes the default above while the doc is live): "use my ollama llama 3.2 which is downloaded and afterwards we will see what to do with claude". The default preset is **free**: Groq `llama-3.3-70b-versatile` for extract/tailor/cover/fact_check and local Ollama `llama3.2` for score explanations. A **local** preset (all Ollama) and a **claude** preset are switchable in Settings.
    - Embeddings use the local Ollama `nomic-embed-text` (already installed) instead of sentence-transformers.
    - User ruling 2026-10-28: the local model is **`qwen3:4b`** via Ollama ("i have downloaded the qwen model so instead of ollama we will use it"; Ollama remains the runtime). `llama3.2` was removed. This qwen3:4b build always emits reasoning ending in `</think>` even with `think:false` (tested 2026-10-27, tier 3), so the app strips everything up to and including `</think>` from Ollama replies. Models are stored at `E:\ollama\models`.

## What the user sees
- Who: Jai, the single user, on a local browser at `http://localhost:5173`.
- "I paste a career link and the tool pulls all its latest jobs and suggests the ones that fit me" (user's words, 2026-10-27) → "Check company" with link + company, or just the company name.
- "I import my sheet" → it becomes the company directory, with each company's detected ATS type.
- "I type a company and see its latest jobs that fit me" → that company's jobs, newest first, each with a match score and reasons; the check reports found/new/closed or why nothing was found.
- "The company isn't in my sheet" → the app suggests careers links; I confirm one.
- "I have a single job link" → add job by URL; paste the description if the page can't be read.
- "I pick a job and get a tailored CV and cover letter" → PDF previews plus a change list showing every reworded bullet next to its original; nothing new is invented.
- "I paste a job description and get a CV with the maximum ATS score" (2026-10-28) → Tailor CV page: ATS score before/after, missing keywords to confirm, accept/revert per change, one-page PDF.
- "I give a person's name and company and get their email address" (2026-10-28: address only, no message text) → ranked addresses with labels and evidence.
- "I enter a name and company and get the email" → ranked addresses with labels, confidence and evidence links.
- "I track what I applied to" → state board and follow-up list.
- Surfaces: Sources, Jobs (split view: list + job panel with Overview/CV/Cover/Application tabs), CVs, Contacts, Find email, Tracker, Settings.
- UI (user ruling 2026-10-27, "modern, simple to navigate and smooth"): Tailwind + shadcn/ui, a collapsible sidebar + Ctrl+K command palette, light/dark following the system, a split-view jobs list, skeletons, toasts, optimistic updates, subtle motion.
- Would find odd, and how it's handled: (1) a site showing zero jobs: the source health shows why (blocked, rate-limited, no matches). (2) Guessed emails bouncing: labels and confidence make the guesses explicit. (3) Tailored CV sometimes barely changes: correct, because reword-only limits it; the keyword coverage report says which JD terms are absent from the CV.

## Consequences
- Enables: adding any career link quickly; switching LLM provider with no code change; truthful tailoring with an audit trail.
- Makes harder: JD skills absent from the CV can never appear in tailored output (by design). JavaScript-heavy custom sites depend on AI extraction and may break.
- Retired: nothing.
- Revisit if: ATS feeds are blocked (reverse condition); the user later wants auto-apply, email drafts or scheduling (each is an additive module).
